# 2026-09-10 WavePaint 工作日志

## 本轮目标

1. 根治用户报障：「本地仿真失败，反正请求无响应的问题」「每次点击仿真的时候必须调用仿真
   服务，必须仿真成功」——不是加提示、加重试，而是把「服务不在线」这件事本身消灭掉。
2. 顺手清理上一轮遗留：换版本后首次启动必崩（见下「根因 ④」），这次必须一并修掉。

> 本轮是**服务在线性（availability）专项**，不是新功能；#86 / #76 主线**未开工**。

---

## 一、根因分析（先说结论，四条并存，缺一不可）

页面与本地仿真服务是「同一台机器上的两个进程」：页面由 exe 内嵌 HttpListener 提供，
页面所有 `/api/sim` 都打在 exe 的端口上。历史上「点仿真无响应」有 **四类** 独立死因：

1. **进程死**：exe 退出/被杀 → 端口上没东西监听 → `fetch` 立刻
   `ERR_CONNECTION_REFUSED`。旧实现只弹一句「请重启应用」——用户能做的只有关掉重开。
2. **换端口**：旧版每次启动随机端口 → 已经打开的页面（origin 钉死在旧端口）永远连不上，
   刷新也没用（刷新还是那个死 origin）。
3. **端口被占**：别的程序占了同一端口 → 页面把 `/api/sim` 发给了「别人的」本地服务，
   拿到 404/乱码，报错还很难看。
4. **换版本后首次启动必崩（本轮新发现，真凶之一）**：`WavePaintLauncher.cs` 里 `ivlRoot`
   **只在 cache 命中分支**被赋值；换版本后首次启动走的是 extract 分支 → `Path.Combine(null, …)`
   → `ArgumentNullException` → **服务根本没起来**。日志实证（`%TEMP%\WavePaintClean_sim.log`）：
   - `19:57:24  BOOT resources=extract` → `IVL repair failed: ArgumentNullException path1`
     （旧代码：崩在资源准备，服务未监听任何端口）
   - `20:06:38  BOOT resources=extract`（修复后）→ 直接 `SERVER start pid=11464 port=17817`
     + 首次仿真 `RUN compile primary 0` / `RUN vcd 985` —— **换版本首次启动不再崩**。

> 这条也解释了「我什么都没改，重启一下就仿真不了了」的历史反复：**每一次 exe 重建**
> 都会让下一轮启动走 extract 分支，旧代码就必崩一次。

## 二、做了什么

### A. `WavePaintLauncher.cs` —— 服务侧根治（+615 行级别改动）

- **固定首选端口**：新增 `const int PreferredPort = 17817`。页面 origin 跨会话稳定，
  从根上消灭「换端口 ⇒ 老页面连不上」。
- **身份标识**：`const string PingTag = "WAVEPAINT-SERVICE"`；`/api/ping` 应答
  `PingTag + "\n" + listenPort + "\n" + buildStamp + "\n"`，并带 `Cache-Control: no-store`。
  前端据此区分「本应用」与「占了同一端口的第三方服务」，绝不误认。
- **`ivlRoot` 崩溃修复（根因 ④）**：
  - extract 分支末尾**统一** `ivlRoot = Path.Combine(root, "ivl")`（不再只在 cache 分支赋值）；
  - 新增 `EnsureIvlReady(out string error)` 二次兜底；
  - **每轮仿真前**也调一次 `EnsureIvlReady`：iverilog 不在了就从内嵌 `ivl.zip` 现补，
    补不了返回可读中文错误（而不是静默 500）。
- **协议重拉（关键交互设计）**：
  - `ParsePortArg(uri)` 手写解析 `wavepaint://start?port=49234`；
  - `MainCore` 区分 `protocolLaunch` + `requestedPort`；
    `StartServer(requestedPort > 0 ? requestedPort : PreferredPort)`；
  - 单实例互斥：已有活实例 → `OpenExistingInstance()`；互斥被占但探不到活服务 →
    记 `TAKE-OVER` 后继续自起（避免死进程永久霸占单实例锁）；
  - 启动失败 → 换新端口重试一次（兜底，不影响正常路径）。
- **发现与自检**：`PublishDiscovery()`（端口文件）、`SelfCheck()`、`HttpGetPing(Proxy = null)`、
  `IsSameOrigin()`（本实例端口 + 任意回环都放行，让跨端口重连成为可能）。
- **窗口探测改为真值**：`FindWaveWindowHandles()` 枚举全部可见顶层窗口（与
  `CloseLegacyWindows()` 同源，真值来源唯一）；`HasWindow()` 探测失败时**返回 true 保守**；
  退出条件收紧为 `everSeen && windowProbeOk && gone > 24 && idle > 90000`。

### B. `js/core/service-guard.js` —— 新增页面侧守卫（192 行，普通 script）

加载顺序：`heartbeat.js` 之后、`ui-bridge.js` 之前（ui-bridge 是 ESM/defer 语义，普通
script 先执行，保证 `window.WPServiceGuard` 在 ui-bridge 用到时已就绪）。

- `pingOrigin(origin, timeoutMs)`：带 `PING_TAG` 校验的判活；返回 `{origin, port, version}`。
- `ping()`：同源探活（页面自己就是服务端提供的，命中率最高）。
- `discover()`：同源 + `http://127.0.0.1:17817` 两个候选依次探测。
- `waitForService(timeoutMs, intervalMs)`：轮询等待上线。
- `relaunch()`：用 **隐藏 iframe** 加载 `wavepaint://start?port=<本页端口>`；
  **不是顶层跳转** —— 协议未注册时顶层跳转会顶掉当前页面，用户未保存的画布内容就没了。
- `recover(options)` → `{ state: 'alive' | 'restarted' | 'elsewhere' | 'dead', origin, port }`：
  - `alive` 服务就在本页 origin（刚才只是抖动）；
  - `restarted` 刚把 exe 拉起来且同源，可直接重试；
  - `elsewhere` 服务在**另一个**回环端口 → **只上报，不自动跳转**（本应用没有自动保存，
    跳转 = 丢未保存内容）；由调用方把 `simApiBase` 指过去；
  - `dead` 确实起不来 → 调用方给手动指引。

> ⚠ `relaunch` 能生效的前提：浏览器允许「外部协议」。协议 URL 由隐藏 iframe 加载时，
> 即使**没有用户手势**也能拉起 exe（实测，见验证 §3）；但首次浏览器会弹一次
> 「是否允许打开 wavepaint:」确认框，用户勾选「始终允许」后无感。

### C. `index.html`

- `heartbeat.js` 之后插入 `<script src="js/core/service-guard.js"></script>`（附注释说明
  为什么必须早于 ui-bridge、为什么是普通 script）。
- `#sim-status` 之后新增 `<button id="sim-recover" type="button" style="display:none;…">启动本地仿真服务</button>`
  —— 服务彻底死亡时的手动自愈入口（默认隐藏，由 ui-bridge 在需要时亮出）。

### D. `js/sim/ui-bridge.js` —— 页面侧自愈接线（+142 行）

- 新增 `let simApiBase = ""` + `simApiUrl(path)`：自愈到「另一个回环端口」时把 `/api/sim`
  指过去（服务端对回环 origin 放行 CORS，`text/plain` 属简单请求不触发预检）。
- 探活拆两层：
  - `probePlainPing(timeoutMs)`：裸 `GET /api/ping` 兜底（dev-server / 旧 exe 只回 `OK`）；
  - `probeServerAlive(timeoutMs)`：`tagged || plain || relocated` 三者任一为真即算在线
    （`relocated` 用于已经切到别的 origin 后不再误判离线、反复触发自愈）。
- `recoverService(options)` / `showRecoverHint()` / `showRecoverPending()`：
  - `showRecoverPending()` 是本轮新增 —— 自动恢复**进行中**先把手动按钮亮出来
    （用户可以立刻点，不必干等），但文案**不说「失败」**；
  - 旧实现在 catch 里先弹「自动恢复失败」再继续尝试自动拉起，字样一闪而过很误导，已替换。
- `/api/sim` 失败 catch 分支重写为三段自愈：
  1. 服务在线 → 只给准确文案（iverilog 超时 / 请求被丢弃），直接 return（行为不变）；
  2. 不在线 → ① `recoverService({ allowRelaunch: false })` 快速发现（~1s，不重拉）：
     `alive`/`elsewhere` → 设好 `simApiBase` → 自动重试一次（`simAutoRetried` 限一次）；
  3. 进程真死 → ② `showRecoverPending()` 亮手动入口 → `recoverService({ allowRelaunch: true, waitMs: 15000 })`
     → 成功自动重试；失败 → `showRecoverHint()` 保留手动按钮 + 中文指引。
- `#sim-recover` 点击：`recoverService({ allowRelaunch: true, waitMs: 20000 })` → 成功即重试仿真；
  `#sim-run` 点击复位 `simAutoRetried` 并收起按钮；仿真成功也收起按钮。

### E. `tools/dev-server.mjs`

- `/api/ping` 由 `res.end('OK')` 改为 `'WAVEPAINT-SERVICE\n' + port + '\ndev-server\n'` +
  `Cache-Control: no-store` —— 与 exe 身份标识格式对齐；否则前端身份校验会把
  dev-server 判成「离线」，本地开发时自愈逻辑会误触发。

## 四、关键结论（交给下一位 AI）

1. **「点仿真无响应」今后应视为 bug**：正常路径必须是「点 → 服务在 → 仿真成功」。
   任何形态的「请重启应用」都只是兜底，不是答案。
2. **端口固定 17817 是刻意设计**，不是巧合：页面 origin 稳定 ⇒ 跨会话可重连、
   localStorage 稳定（顺带缓解 #81 Bug3 教程重跑）。改端口策略前先读
   `memory/06-PITFALLS.md` P29。
3. **恢复策略一律「改 `simApiBase` / 同端口重拉」，禁止自动整页跳转**：
   本应用**没有自动保存**，跳转 = 用户画布内容全丢。见 P30。
4. `relaunch()` **必须用隐藏 iframe**：顶层跳转 / `window.open` / `<a target=_blank>`
   都会被浏览器的用户手势策略拦下（实测），且顶层跳转在协议未注册时还会顶掉页面。
5. 换版本后首次启动走 extract 分支 —— 这是**每轮重建 exe 后都会遇到**的路径，
   任何「只在 cache 分支初始化」的写法都是定时炸弹。见 P28。
