# 调研：核心混淆代码解混淆 + 原生 UI 1:1 复刻可行性

> 目的：评估能否去除对混淆的依赖（解混淆后自行维护）以及能否在原生 UI 上 1:1
> 复刻，给后续方向提供决策依据。WavePaintSim 是基于 `js/wavepaint.63e6dade.js`
> 这一个混淆核心构建的（1.4MB 单行 JS，obfuscator.io 风格）。

---

## 一、核心文件指纹（实测数据）

| 指标 | 数值 | 含义 |
|------|------|------|
| 文件大小 | **1,435,024 字节**（≈ 1.37 MB） | 单文件单行 |
| 语句数（按分号粗分） | **7,288** | 平均每行 ~200 字节 |
| 混淆标识符种类 | **19,460** | `_0x` + 4~8 位 hex |
| 十六进制常量 | **92,423** | `0x...` 形式（混淆器用 hex escape 数字） |
| 字面量字符串 | **14,663** | 已被字符串数组替换的大多数 |
| 字符串数组声明 | **31** | `const _0xXX = [...]` 形式 |
| 字符串解码函数 | **1**（`_0x55bf`） | 被全文件 ~7,288 处调用 |
| 控制流平坦化 dispatcher | **1**（`while(!![])`） | 标志性 obfuscator.io CF 模式 |
| 顶级 var/let/const 行 | 1 | 多变量同行声明 |
| `debugger;` trap | 0 | 没有反调试陷阱 |
| sourceMappingURL | 0 | **无 source map**（sourcemap 丢失/未发布） |
| 其它混淆器版本线索 | 无 | 无版本字符串 |

**判断**：obfuscator.io v3/v4 高级配置（stringArray + hex + controlFlowFlattening）。
无 debugger 反调试但有控制流平坦化（让静态分析极其困难）。

## 二、解混淆可行性

### 2.1 可以做到的（部分还原）

| 内容 | 可行性 | 工具 / 方法 |
|------|--------|-------------|
| 字符串还原 | ✅ **完全可行** | 用 hook 拦截 `_0x55bf(idx)` 或静态分析字符串数组 + 替换调用点 |
| 十六进制常量十进制化 | ✅ 完全可行 | 简单的 AST 转换（ast-grep + jscodeshift） |
| 格式化（折行+缩进） | ✅ 已有 | `tools/probe-core.mjs` 已按分号粗分；js-beautify 可美化 |
| 字符串数组 rotate 反推 | ✅ 可行 | 字符串按 `i % len` 访问，`len` 已知就能直接读数组 |
| 控制流平坦化部分还原 | ⚠️ **部分可行** | obfuscator-io-deobfuscator（npm）能处理部分场景，但本例 dispatcher 与业务深度耦合，**预计 60%~80% 还原**，剩余需要人工 |
| 函数参数重命名 | ⚠️ 半自动 | 用工具把 `_0xXX` 重命名为 `arg1/arg2/...`，可读性提升 |
| 死代码消除 | ⚠️ 部分 | 有些分支永远不进，tree-shaking 类工具能清理 |

### 2.2 做不到的（永久丢失）

| 内容 | 原因 |
|------|------|
| **原始标识符名** | obfuscator.io 生成的字典重命名是**单向**的（除非有映射字典泄露）。`drawRangeSelection` 这种有意义的名字彻底丢失，恢复成 `_0x23bc4` |
| **原始代码注释** | 混淆前剥离，永久丢失 |
| **类型注释（TS Flow）** | 未提供，无可恢复 |
| **控制流分支意图** | dispatcher 模式（`while(!![])` + `switch(_0x) { case 0: ... case 1: ... }`）把代码切成碎片，重组时**条件/循环边界**会模糊 |
| **复杂对象方法语义** | 比如 `MmayC`、`LkJYs` 这些动态键名（`obj['MmayC']()`）混淆为字符串后**仍可还原为字符串**，但调用的是哪个方法需要查字符串数组 + 人工对应 |

### 2.3 可用工具体验

| 工具 | 适用 | 实测可用性 |
|------|------|-----------|
| **ast-grep / jscodeshift** | 字符串/数字还原 | ✅ 可写 codemod 脚本 |
| **obfuscator-io-deobfuscator**（npm） | 字符串/数字/CF 部分 | ⚠️ 对本例可能只能还原 60% |
| **webcrack** | 端点提取 | ✅ 适合网络请求分析，但本核心是纯 UI 库 |
| **jsnice**（ML） | 变量名恢复 | ❌ 对纯混淆（无源码）效果差 |
| **de4js** | 基础美化 | ✅ 但仅美化 |
| **sourcemap-reverse** | 反推源 | ❌ 无 sourcemap，无源 |
| **自定义 probe**（已用） | 关键函数转储 | ✅ **tools/probe-core.mjs** 已在用 |

**本项目已有最佳实践**：`tools/probe-core.mjs` 按分号切分 + 关键词搜索 + 连续语句段转储
（已成功定位 #3208/4406/4608/4753/4816/4822/4825/4918/6621 等关键状态机），是
**针对本核心最高效的"局部解混淆"**。

### 2.4 解混淆的实际收益评估

| 方案 | 预期收益 | 投入 | 建议 |
|------|----------|------|------|
| 全自动解混淆 → 干净 JS | ❌ 变量名永久丢失、CF 难解；**不可达"干净"** | 高 | 不建议 |
| 字符串+数字还原 + 格式化 | ✅ 可读性显著提升 | 中（1~2 周人） | 一次性价值，长期维护收益递减 |
| 控制流部分还原 | ⚠️ 60%~80%，剩余必须人工 | 高（2~4 周人） | 性价比低 |
| **针对关键函数的局部解混淆** | ✅ 高 ROI | 低（已用 probe-core） | **继续采用** |

## 三、原生 UI 1:1 复刻可行性

### 3.1 UI 部分（HTML + CSS）

| 资源 | 规模 | 可行性 |
|------|------|--------|
| `index.html` | 671 行（未压缩） | ✅ 完全可读、照抄。**1:1 复刻可行** |
| `css/wavepaint.e7b903ef.css` | 压缩为 2 行（实际 ~30~50KB） | ⚠️ 需先格式化（js-beautify/css-beautify）；类名是 obfuscator.io 风格（`._XX`），但**行为可复刻**（`#sim-panel { ... }` 这类选择器也照抄即可） |
| 资源（img/） | 23 个 SVG/ICO/WEBP | ✅ 直接复制 |

**UI 复刻结论**：**完全可行**。是 WavePaintSim 已经在做的事（已照搬 index.html + CSS
加载到自定义 `index.html` 中通过 `wpf.*` 扩展）。

### 3.2 功能部分（1.4MB 混淆 JS）

**功能模块清单**（从 probe-core 与 window API 推断的核心模块）：

| 模块 | 估计行数 | 难度 | 复刻价值 |
|------|----------|------|----------|
| 画布渲染（drawWaveform + drawBitSignal + drawBusSignal + drawArrow + drawMarker...） | ~3000 行 | 高 | 必要（UI 核心） |
| 鼠标/键盘事件路由（mousedown/move/up/keydown + rangeSelecting 状态机） | ~500 行 | 中 | 必要 |
| 工具切换（currentTool + 工具按钮 click + 状态守卫） | ~200 行 | 中 | 必要 |
| 信号管理（添加/删除/排序/m_signals 维护） | ~400 行 | 中 | 必要 |
| 撤销/重做（pushUndoSnapshot + signalList 序列化） | ~300 行 | 中 | 高 |
| 复制/粘贴（clipboard + pastePreview） | ~200 行 | 低 | 高 |
| range selection 框选（drawRangeSelection + rangeSel* 状态） | ~300 行 | 中 | 必要 |
| JSON 导入导出（loadDocFromLink + 下载） | ~300 行 | 低 | 高 |
| VCD 导入 | ~200 行 | 中 | 中 |
| 模板系统（feature-templates 已在外部） | ~? | 中 | 中 |
| TB 生成（已在 sim-bridge / sim.js） | 已在外部 | — | — |
| 仿真编排（sim-* 按钮） | 已在外部 | — | — |
| 文本标注、箭头、时间跨度、时间跳转 | ~800 行 | 中 | 中 |
| 主题（dark/light） | ~100 行 | 低 | 低 |
| 画布缩放/平移 | ~300 行 | 中 | 必要 |
| 信号名编辑、宽度编辑、属性面板 | ~500 行 | 中 | 中 |

**复刻所有功能**：估算 **1.5~2.5 人月**（熟练工程师 8 周 ~ 12 周），且需要持续维护
（核心更新后要跟进）。

**复刻必要子集**（WavePaintSim 已做的部分：选框增强、TB 生成、值编辑、绘制插值、撤销）：
已用 19 轮迭代、约 **5,000 行 feature-*.js** 完成核心交互的扩展。本质是"以扩展方式
复用核心，不复刻核心"。

### 3.3 复刻的 1:1 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 行为细节不一致 | 用户的特定交互行为出现差异 | 全量回归 + 用户实测 |
| 性能差异 | 渲染卡顿 | 沿用相同算法（O2/WaveDrom 风格） |
| 长期维护成本 | 核心更新后需同步 | **不复刻是规避此风险** |
| 测试覆盖 | 1.4MB 核心没有自动化测试 | 用户手动验证 |

## 四、推荐策略（决策树）

```
                            ┌─ 短期（1~2 周）：对核心字符串+数字还原为干净 JS
                            │  一次性价值，ROI 中。
                            │
                继续维护扩展─┤
                            │  ★ 长期推荐：保持现状，feature-*.js 扩展模式
                            │  - 零解混淆风险
                            │  - 零复刻工作量
                            │  - 已有 19 轮迭代、5K 行扩展验证可行
                            │
当前在 WavePaintSim ┼───────┤
                            ┌─ 一次性大投入：完整解混淆 + 复刻所有功能
                            │  - 1.5~2.5 人月
                            │  - 长期维护成本
                            │  - 行为一致性风险
                            └─ 不推荐（除非核心不再维护）
```

**核心结论**：
1. **解混淆"完整"不可达**（变量名永久丢失），"部分还原"价值边际递减。
2. **1:1 复刻 UI 可行**（HTML+CSS 照搬），**1:1 复刻功能成本巨大**（1.5~2.5 人月 +
   持续维护）。
3. **当前策略（feature-*.js 扩展）已是最优解**：
   - 0 解混淆成本
   - 0 复刻成本
   - 已有 19 轮迭代验证（regression 34/34、e2e-sim 0 失败、真实浏览器端到端）
   - 核心原生的画布/选择/JSON 导入导出都直接复用
4. **解混淆的唯一持续价值**是 `probe-core` 这类**针对关键函数的局部逆向**，用于：
   - 理解 bug 根因（如本轮子步单击闪一下）
   - 理解 TB 生成的输入约束（`readWaveDocument` → `clockCells`）
   - 估算接口位置（核心的 select 工具 → 哪个函数处理）

## 六、工作量与风险（量级评估）

| 方案 | 一次性工作量 | 长期维护 | 风险 |
|------|--------------|----------|------|
| **当前策略**（扩展） | 0（已完成 ~5K 行） | 每轮 200~600 行 | 极低（核心不变，行为稳定） |
| 字符串+数字还原 | 1~2 周人 | 无 | 低 |
| CF 部分还原 | 2~4 周人 | 核心更新需重做 | 中 |
| 复刻 UI 全部功能 | 1.5~2.5 人月 | 持续（核心更新跟进） | 中高（行为一致性） |
| 1:1 全替代（不解混淆全重写） | 3~4 人月 | 持续 | 高（偏离原始产品） |

## 七、结论与建议

1. **不要尝试完整解混淆**。变量名永久丢失，"干净"代码不可达。
2. **不要尝试 1:1 复刻所有功能**。成本巨大、行为一致性风险高、维护负担重。
3. **继续当前扩展模式**（feature-*.js + 自写工具 + probe-core）。本项目已证明可行。
4. **把解混淆工具作为"理解手段"**，不作为"产出"。probe-core 已是最佳 ROI 工具。
5. **针对核心已知的"行为陷阱"**（如核心的 select 工具下 mouseup 清除选框、Vector
   弹窗、工具按钮 toggle 行为）已在 feature-*.js 层做适配/防御——这是**绕开混淆
   的正确方式**。
6. **如果未来核心停止维护**，再启动"功能复刻"工程（按本报告第 3.2 节模块清单，
   1.5~2.5 人月），在那之前不必做。
