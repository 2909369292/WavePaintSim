## 0. 三个必须先想清楚的前提

### 0.1 这个项目的最大风险不是 Bug，而是"改了不知道有没有坏"

项目当前状态：

- **零自动化测试**（没有单元测试、没有快照测试、没有任何断言）。
- 功能层几乎全部建立在**对混淆核心运行时行为的假设**之上（`mapCanvasPosition` 返回什么、原版在 mousedown 里做没做撤销、`.bit-state-option.selected` 是谁加的……）。
- 8 个 `feature-*.js` 模块通过**捕获阶段 + `stopImmediatePropagation`** 互相耦合，监听器注册顺序就是执行顺序。
- **没有版本控制**（`.git` 不存在，见 `04` BUG-018）。

在这种状态下直接上手改 P0 Bug，很可能出现"修好一个、悄悄弄坏两个，三天后才发现"。

**所以本路线图的第一阶段不是修 Bug，而是先装安全网。**

### 0.2 强烈建议：先做 P0，再碰任何 Bug

```
P0  建立安全网     git init + 最小回归测试        ← 半天，收益贯穿全程
P1  止血           修 4 个会给出错误结果的 Bug     ← 1~2 天
P2  测试网         数据模型断言 + TB 生成快照测试  ← 1 天
P3  稳定性+正确性  修 6 个中危                     ← 2~3 天
P4  功能补齐       F9/F10 + 既有任务书的 A/C/D/E   ← 视需求
P5  工程卫生       清理、加固、可观测性            ← 择机
```

如果对"先建测试"有顾虑，至少**先做 `git init`**（1 分钟，零风险）。

### 0.3 关于工作量的诚实说明

下面的"预计"是**粗估**，基于代码改动量与验证复杂度，不是承诺。
本项目的真实时间主要消耗在**构建-启动-手工验证**的循环上（每次改 JS 都要重建 exe，见 `01` 第 5 节）。
**把 P0 的 dev-server 调试链路打通，能把后续所有阶段的时间成本砍掉一半以上。**

### P1 的执行要点

**BUG-001**：推荐方案是加一个 `replaying` 重入标志，而不是删掉回放逻辑。
需要同时认清一个事实：**即使修好了递归，回放也永远不会生效**——因为 `onMouseDown` 里的 `stopImmediatePropagation()` 会挡住核心挂在 canvas 上的目标阶段监听器。
所以"单击回放原版行为"这个设计目标**在当前架构下无法用 dispatchEvent 实现**，要么改为直接调用核心 API，要么明确放弃该行为。详见 `03`。

**BUG-003 的修复方式已被 P0 的发现改写**：
核心自带 `document_wave.pushUndoSnapshot()`（见 `04` §0 订正 3）。
所以正确做法是：在 `feature-draw.js` 的 `onMouseDown` 里**调用一次** `window.document_wave.pushUndoSnapshot()`，
**不要**在 `onMouseMove` 里调（否则一次拖拽会压几十上百个快照，瞬间撑爆 100 条上限，把真正需要保留的历史挤掉）。

```js
function onMouseDown(e) {
  // ... 前置判断 ...
  const hit = hitTest(e);
  if (!hit) return;
  e.stopImmediatePropagation();
  e.preventDefault();
  // 拦截掉了核心的 mousedown，它本来要压的撤销快照得由我们补上（整次拖拽只压一次）
  const dw = window.document_wave;
  if (dw && typeof dw.pushUndoSnapshot === 'function') dw.pushUndoSnapshot();
  else wpf.pushUndoSnapshot();
  drag.active = true;
  paintAt(e);
}
```

**BUG-002 需要特别小心**：`matchSignalsToPorts` 的 fallback 逻辑改掉后，
原本"能跑出结果（虽然结果错）"的用例会变成"报未绑定错误"。
这是**正确的行为改变**，但需要有心理准备：**修复后你会第一次看到有多少端口真的没绑定上。**
建议同时在 UI 上把未绑定端口显示出来（这本来就该有）。

### P2-1 数据模型不变式断言 ⏱ 2h

把 `01` 第 3 节的"铁律"变成可执行断言。建议做成 `tools/check-model.mjs` 或页面内的 `wpf.assertModel()`：

```js
// 在每次重绘后、每次批量操作后调用
wpf.assertModel = function (where) {
  const dw = window.document_wave;
  if (!dw) return;
  const stride = dw.m_subStepCount + 1;
  const expect = dw.m_sampleCount * stride;
  const bad = [];
  (dw.m_signals || []).forEach(function (sig, i) {
    if (!sig) return;
    if (sig.type === window.SignalType.BlankRow) return;
    if (!Array.isArray(sig.values)) { bad.push(i + ' values 非数组'); return; }
    if (sig.values.length !== expect) {
      bad.push(i + ' (' + sig.name + ') values.length=' + sig.values.length + ' 期望 ' + expect);
    }
    ['labels', 'segmentStyles', 'driveStrengths', 'clockMarkers', 'waveDromColorCodes']
      .forEach(function (k) {
        if (Array.isArray(sig[k]) && sig[k].length !== expect) {
          bad.push(i + '.' + k + ' 长度 ' + sig[k].length + ' 期望 ' + expect);
        }
      });
    // 类型检查：Bit 信号必须是数字
    if (sig.type === window.SignalType.Bit) {
      for (let j = 0; j < sig.values.length; j++) {
        const v = sig.values[j];
        if (typeof v !== 'number') { bad.push(i + ' values[' + j + '] 类型=' + typeof v + '（Bit 必须是数字）'); break; }
      }
    }
  });
  if (bad.length && window.console) {
    console.error('[模型不变式] ' + where + ' 违反：\n  ' + bad.join('\n  '));
  }
  return bad;
};
```

**在哪些地方调用**（临时用，验证完可保留为 debug 开关）：
`wpf.scheduleRedraw()` 内部、`feature-resize.resizeSignals()` 末尾、每个 `feature-*` 的写入操作末尾。

### 5.3 处理建议

**不要同时开工。** 两份清单有重叠区域（尤其是 A 与本次的 BUG-002，都影响仿真正确性；D 与 BUG-003，都在 `feature-draw.js`）。

推荐顺序：

```
1. 先做本次审计的 P0 + P1（安全网 + 4 个止血 Bug）
      ↓  因为 A 的修复会动 feature-draw.js，而 BUG-003 也要动同一个文件
2. 再做既有任务书的 A（仿真结果为 0）
      ↓  A 的根因（只写单格）与 BUG-003 的修复位置（onMouseDown 压快照）
         在同一个函数 paintAt / onMouseDown 上，一起改一次验证
3. 然后 C / D / E（UI 与交互增强，风险最低）
4. 最后 F9 / F10
```

**特别提醒 A 与 BUG-003 的关系**：

文档 §2.3 要求 `paintAt()` 写入**整个主步的所有 stride 个下标**。
这会让一次绘制修改的数据量变为原来的 `stride` 倍（子步为 3 时是 4 倍）。
而 BUG-003 的修复是"整次拖拽只压一次快照"——**两者配合得很好**，但如果先做了 A 再按"每次 mousemove 压快照"的错误方式修 BUG-003，内存会涨得更快。
**务必先确定 BUG-003 的修复策略（整次拖拽一次快照），再做 A。**

### 5.4 顺手修的小问题

- `js/feature-common.js:173` 的注释 `// ---- 编辑粒度 ----` 与实际代码（`clamp` / `el`）**不符**，是陈旧注释。
