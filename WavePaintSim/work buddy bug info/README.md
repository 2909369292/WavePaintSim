## 0. 请先读这一节（最重要的四件事）

1. **不要修改混淆核心** `js/wavepaint.63e6dade.js`（1.43 MB，obfuscator.io 深度混淆，字符串运行时解码）。
   项目已确立的架构原则是：**混淆核心只当"引擎"，所有新功能通过新增独立模块 + DOM 事件接管 + 全局 API 调用实现**。
   这条原则被严格贯彻，请继续保持。
2. **数据模型铁律**（详见 `01-项目背景与架构.md`）：
   `signal.values.length === m_sampleCount × (m_subStepCount + 1)`。
   任何违反此式的代码都会导致绘制 / 导出 / 仿真采样同时错位，而且**症状离病因很远，极难排查**。
3. **改完 JS 必须重建 exe 才生效**（资源被内嵌进 `WavePaint.exe`，刷新页面无用）。流程见 `01-项目背景与架构.md` 第 5 节。
4. **★ 核心自带 `document_wave.pushUndoSnapshot()`，请直接复用它。**
   混淆核心在 `WaveDocument.prototype` 上暴露了这个方法（核心内部共调用 **32 次**），
   它自带**撤销栈 100 条上限裁剪**和 **redo 栈清空**。
   `feature-common.js` 手写的 `wpf.pushUndoSnapshot()` **没有上限裁剪**，会无限增长。
   注意两者**同名**（`window.document_wave.pushUndoSnapshot` vs `window.__wpf.pushUndoSnapshot`），极易混淆。
   详见 `04-BUG清单-中低危与隐患.md` §0 订正 3 与 §3。

## 5. 给接手 AI 的四条工作建议

1. **先建测试网再动刀。** 项目目前没有任何回归测试，而功能层完全依赖对混淆核心行为的假设。建议按 `05-改进路线图` 的 P2 步骤，先建立数据模型断言 + TB 生成快照测试，再做其它修改。
2. **每次改动只碰一个模块。** `feature-*.js` 之间通过 `window.__wpf` 共享状态（`cursor` / `selection`），且都使用捕获阶段事件 + `stopImmediatePropagation`，监听器注册顺序会影响行为（见 `01-项目背景与架构.md` 第 6 节）。批量改写容易引入难以复现的交互 Bug。
3. **不要试图反混淆核心，但可以静态探测它。** 不要做完整反混淆（主字符串表约 6632 项、运行时解码，投入产出比极差）。但**针对性的静态探测非常有效**——本次审计中，"核心自带 `pushUndoSnapshot()`"、"撤销栈上限 100"、"`mapCanvasPosition` 的 null 条件"这三个关键结论都是静态探测得到的，其中一个直接改变了两个 Bug 的最优修复方案。
4. **探查核心时，直接 grep 属性名会搜不到。** 混淆器把字符串拆成了 `'m_undoStac'+'k'`、`'pushUndoSn'+'apshot'`、`_0x27d135(0x1773)+'apshot'` 这类形式（直接搜 `m_undoStack` / `snapshot` 的结果都是 **0**）。
   正确做法是**搜片段再提取上下文**，例如用 Python 定位 `'apshot'`、`m_undo` 这样的子串；
   或者更省事——**直接在浏览器控制台里做运行时实验**（`typeof document_wave.pushUndoSnapshot`、`document_wave.m_undoStack.length`）。运行时验证永远比静态推测可靠。
