# 01 — 项目背景与架构

> 动手改代码前必读。本节内容是后续所有 Bug 分析与修复方案的前提。

---

## 1. 这个项目是什么

**一句话**：把商业在线波形编辑工具 WavePaint（`https://www.wavepaint.net/app/`）的静态前端抓取下来，做离线化 + 汉化 + 去商业化，然后在其上**外挂**一套 Verilog 仿真能力，最后用 C# 启动器把「全部前端资源 + Icarus Verilog 工具链」打包成单个 `WavePaint.exe`。

**目标形态**：完全离线、免安装、免管理员权限，仅需 Windows 10/11 + Microsoft Edge。

**项目定位**：不是从零开发，而是**在不可修改的第三方混淆代码之上做增强**。这个定位决定了整个架构。

### ⚠ 关键事实：存在两套并行实现，其中一套是死代码

| 实现 | 文件 | 状态 |
|---|---|---|
| **A（运行时）** | `index.html` + 混淆核心 + `feature-*.js` + `sim-bridge.js` | ✅ 真正在跑 |
| **B（死代码）** | `js/app.js`(1072行) + `js/renderer.js`(270行) + `js/utils.js`(21行) + `css/styles.css` | ❌ **从未被 `index.html` 引用** |

> **给接手者的建议**：不要误以为 `app.js` 是主程序去改它。要么删除，要么明确标注后移入 `attic/`。详见 `04-BUG清单` BUG-015。

注意 `js/model.js` 与 `js/sim.js` **不是**死代码——它们被 `sim-bridge.js` 间接 import。

## 3. 数据模型铁律（最重要的一节）

### 3.1 核心对象

```
window.document_wave (WaveDocument 实例)
 ├─ m_sampleCount    : 主步数（UI「步数」，默认 30）
 ├─ m_subStepCount   : 子步数（UI「子步数」，默认 1）
 ├─ m_signals[]      : Signal 对象数组
 ├─ m_markers / m_timeJumps / m_timeSpanMarkers / m_arrows / m_textAnnotations
 └─ m_undoStack / m_redoStack
```

### 3.2 ★★★ values 长度公式

```
values.length === m_sampleCount × (m_subStepCount + 1)
```

每个时间步在 `values` 数组中占 `(子步数 + 1)` 个下标。**主值约定**：每个时间步的**第 1 个值**（下标 = `步号 × (子步+1)`）代表该步的值，其余下标是该步内部的子步。

实测数据：
| 步数 | 子步 | values 长度 |
|---|---|---|
| 30 | 1 | 60 |
| 30 | 2 | 90 |
| 50 | 1 | 100 |
| 20 | 1 | 40 |

> **违反此公式 = 绘制 / 导出 / 仿真采样同时错位**，且症状离病因很远。这是本项目历史上"波形格式不严谨"反馈的根因（已由 F1 修复，见 `02-功能规划与完成度.md`）。

### 3.3 位值编码

| 信号类型 | values 元素类型 | 取值 |
|---|---|---|
| Bit（`SignalType.Bit`） | **数字** | `0`=低，`1`=高，`-1`=未定义(x)，`2`=高阻(z)，`3`=上拉(u)，`4`=下拉(d) |
| Vector（`SignalType.Vector`） | **字符串** | 如 `"0000"` / `"xxxx"` / `"f"` |
| BlankRow | — | 不绘制 |

跨层转换函数：
- `js/sim-bridge.js:36` `toNativeBitValue(str)` → 数字
- `js/sim-bridge.js:47` `fromNativeBitValue(num)` → 字符串
- `js/feature-common.js:93` `wpf.bitStateToValue(state)` → 数字

### 3.4 Signal 字段清单

`name, type, width, msb, lsb, values[], labels[], segmentStyles[], driveStrengths[], clockMarkers[], waveDromColorCodes[], edgeArrow, color, fill, riseTime, fallTime, subSteps, isClockPattern, clockHighSamples, clockLowSamples, showClockMarkers, uiRowHeightHint, groupName, groupColor, groupPath, radix`

> ⚠ **两套数据约定不一致**：`feature-common.js:154` 的 `syncSignalMeta` 把 `driveStrengths` 填成数字 `0`；而 `app.js`（死代码）的 `resizeMetaArray` 填成字符串 `"strong"`。修复时以**运行时实现（数字）为准**。

### 4.3 ★★ `WaveDocument.prototype.pushUndoSnapshot()`（本次审计最重要的发现）

混淆核心在 `WaveDocument.prototype` 上暴露了一个方法，名字就叫 **`pushUndoSnapshot`**。
在核心中它被调用了 **32 次**（`addSignal` / `deleteSignal` / `moveSignal` / `setArrowStyle` / `clearTimeJumps` / `setMarkerColorById` … 全都在改数据前调用它）。

反混淆后的等价实现（原文中字符串被拆成 `'m_undoStac'+'k'`、`'pushUndoSn'+'apshot'`）：

```js
WaveDocument.prototype.pushUndoSnapshot = function () {
  const snap = {
    signals:         JSON.parse(JSON.stringify(this['m_signals'])),
    markers:         JSON.parse(JSON.stringify(this['m_markers'])),
    timeJumps:       JSON.parse(JSON.stringify(this['m_timeJumps'])),
    timeSpanMarkers: JSON.parse(JSON.stringify(this['m_timeSpanMarkers'])),
    arrows:          JSON.parse(JSON.stringify(this['m_arrows'])),
    textAnnotations: JSON.parse(JSON.stringify(this['m_textAnnotations'])),
    sampleCount:     this['m_sampleCount'],
    subStepCount:    this['m_subStepCount']
  };
  this['m_undoStack'].push(snap);
  if (this['m_undoStack'].length > 100) this['m_undoStack'].shift();  // ★ 上限 100
  this['m_redoStack'] = [];
};
```

**由此得到四个结论：**

| # | 结论 | 影响 |
|---|---|---|
| 1 | **应直接复用 `window.document_wave.pushUndoSnapshot()`** | `feature-common.js` 手写的 `wpf.pushUndoSnapshot()` 应改为对它的委托 + 兜底 |
| 2 | **撤销栈上限是 100 条**，超出后 `shift()` 丢最旧的 | 手写版本**没有**这个裁剪，会无限增长（见 `04` BUG-007） |
| 3 | **快照存的是普通对象**（`JSON.parse(JSON.stringify(x))`） | 所以"structuredClone 会丢失 Signal 原型"这个担忧**不成立**——核心自己存的就不是类实例 |
| 4 | `feature-common.js` 手写的 8 字段格式**与核心逐个字段完全一致** | 现有实现在格式上是对的（纯属巧合地写对了），改成委托后天然一致 |

> ⚠ **命名陷阱**：`window.document_wave.pushUndoSnapshot` 与 `window.__wpf.pushUndoSnapshot` **同名**。
> 在 `feature-common.js` 内部，`wpf.pushUndoSnapshot()` 是后者，`dw.pushUndoSnapshot()` 才是前者。改动时格外小心。

**⚠ 探查核心的方法论提醒**：
混淆器把字符串拆成了 `'m_undoStac'+'k'`、`_0x27d135(0x1773)+'apshot'` 这类形式，
所以**直接 `grep "m_undoStack"` 或 `grep "snapshot"` 的结果都是 0 次**。
正确做法是搜**片段**（如 `'apshot'`、`m_undo`）再提取上下文，或直接在浏览器控制台做运行时验证。

### 4.4 `mapCanvasPosition` 什么时候返回 `null`（已精确确认）

```js
if(!document_wave||!canvas)return null;     // ← 唯一的 null 路径
```

| 情况 | 返回值 |
|---|---|
| `document_wave` 或 `canvas` 缺失（启动未完成 / 已销毁） | **`null`** |
| 点在名称列左侧（`relX < 0`） | 全 `-1` 的哨兵对象 |
| 点在有效波形区内 | 正常对象，各字段为真实值 |
| 其它几何越界（超过最后一步、落在空白行/标尺） | 全 `-1` 的哨兵对象 |

**即：几何越界返回对象（各字段 `-1`），不会返回 `null`。**
`wpf.mapAt()` 里的 `|| null` 因此基本用不上，但也无害。
`feature-select.js` 的 `regionFromPoints()` 里 `Math.max(0, ...)` 把 `-1` 夹成 0 才是真问题（见 `04` BUG-006）。

### 4.5 核心没有做 DPR 缩放（已确认）

在 `js/wavepaint.63e6dade.js` 中检索 `devicePixelRatio` 与 `setTransform`，**出现次数均为 0**。
即主 canvas 的 `width` 属性值与 CSS 宽度基本一致，没有 HiDPI 缩放。
（首轮曾据此怀疑 overlay 叠加层在 HiDPI 下错位，该结论**已撤回**，见 `README.md` 勘误第 2 条。）

## 6. 扩展机制：捕获阶段事件接管（本项目最核心的手法）

所有 `feature-*.js` 都遵循同一模式，范例是 `js/step-commit-patch.js`：

```js
document.addEventListener('mousedown', handler, true);   // ← 第三个参数 true = 捕获阶段
function handler(e) {
  if (!shouldIntercept(e)) return;   // 不满足条件就放行给原版
  e.stopImmediatePropagation();      // ← 彻底阻断后续所有监听器（含原版的目标阶段监听器）
  e.preventDefault();
  // 自定义逻辑
}
```

**为什么用捕获阶段**：混淆核心的监听器挂在目标元素（`#wave-canvas`）上。捕获阶段从 `window` 往下传播，**先于**目标阶段执行，因此可以在原版之前拦截。

### ⚠ 由此产生的两个必须警惕的副作用

1. **监听器注册顺序 = 执行顺序**（同一节点、同一阶段，按注册先后）。`index.html` 中的脚本顺序即注册顺序：
   `feature-draw → feature-resize → feature-shortcuts → feature-select → feature-measure → feature-generator → feature-templates`。
   各模块靠 `data-tool` 判断来避免互相干扰，**改动模块顺序可能引入难以复现的交互 Bug**。
2. **拦截会连带阻断原版的副作用**，不只是绘制逻辑。例如原版很可能在画布 `mousedown` 里压入撤销栈——被 `stopImmediatePropagation` 一并挡掉，这就是 BUG-003 的成因。

### 6.1 `window.__wpf` 共享命名空间

`feature-common.js` 建立，各模块共享：

| 成员 | 用途 |
|---|---|
| `__wpf.ready(fn)` | 等核心就绪（轮询 100ms） |
| `__wpf.mapAt(x,y)` / `__wpf.canvas()` | 坐标映射 |
| `__wpf.signalRowBand(x,y,idx)` | 探测某信号行的 y 范围 |
| `__wpf.currentBitState()` / `setBitState()` / `isAutoBitMode()` | 位状态 |
| `__wpf.currentTool()` | 当前工具（`data-tool`） |
| `__wpf.pushUndoSnapshot()` | 向**原版**撤销栈压快照。⚠ 应改为对核心 `document_wave.pushUndoSnapshot()` 的委托，见第 4.3 节 |
| `__wpf.syncSignalMeta(sig,len)` | 同步 labels/styles 等数组长度 |
| `__wpf.scheduleRedraw()` | rAF 节流重绘 |
| `__wpf.cursor` | feature-draw 写入、feature-shortcuts 读取的方向键光标 |
| `__wpf.selection` | feature-select 写入的框选区域，feature-measure 也读它 |

> `cursor` 与 `selection` 是**跨模块可变共享状态**，改动任一模块时都要检查另一侧的读写。

## 8. 已确认无问题的项（避免重复排查）

- ✅ 全部前端 JS 通过 `node --check` 语法检查。
- ✅ `index.html` 是合法 UTF-8，无中文乱码。（首轮报告为误报，见 `README.md` 勘误）
- ✅ `window.SignalType` 确实存在（核心用 `window[...]=SignalType` 赋值），feature 模块里 `window.SignalType.Bit` 的判断有效。
- ✅ `.bit-state-option.selected` 与 `.tool-btn.active` 类名与核心行为一致。
- ✅ `mapCanvasPosition` 是顶层 `function` 声明，会挂到 `window`（bundle 未被 IIFE 包裹）。
- ✅ `mapCanvasPosition` 返回对象中的字段名（`signalIndex` / `signal` / `clickedOnName` / `mainStep` / `signalSampleIndex` / `signalSubSteps` / `signalDivisor` / `signalEffectiveCount` / `nameWidth` / `relX` / `stepWidth` / `globalStepWidth`）**全部真实存在**，feature 模块的用法正确。
- ✅ `isClockPattern` 是 `Signal` 的**自有数据属性**（非原型 getter），在核心的序列化/克隆路径中设置（偏移 `1417736`）。
  注意：它**不在** `Signal` 构造函数里初始化，所以 `new Signal()` 出来的对象是 `undefined`；
  只有从工程文件载入的信号、或 `sim-bridge.js` 创建的信号（`:84/:113/:227` 显式赋值）才有此字段。
  因此 `feature-resize.js:64` 的时钟周期延续**只对这些信号生效**，对纯新建信号会走"延续最后一个确定值"分支。这是设计使然，不是缺陷，但要知道。
- ✅ 核心**没有** DPR 缩放（`devicePixelRatio` / `setTransform` 出现 0 次），不存在 HiDPI 叠加层错位问题。
- ❌ `window.__wpConstants` **不存在**（`docs/` 文档曾提及，代码里搜不到，勿依赖）。
