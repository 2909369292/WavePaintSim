## 二、★ 核心结论：「恒为 0」的真根因

### 仿真引擎本身是好的

场景「DFF + clk 方波 + d 脉冲」→ 输出 `q = x000011111100000`，**完全正确的 D 触发器行为**。
链路 [5]~[10]（payload → iverilog → vvp → VCD 解析 → 回填）**没有问题**。

### 真根因：未绑定输入端口的默认激励是「全 0」，而 `rst_n` 是低有效复位

默认 RTL 就是 `counter`（`sim-bridge.js:4-17`），带 `input rst_n`，`always @(posedge clk or negedge rst_n) if (!rst_n) q <= 4'd0;`

`buildAutoTestbench`（`js/sim.js:546-555`）对**未绑定**的输入端口生成**全 0** 激励：

```js
values: Array.from({ length: defaultSignal.values.length }, () => (defWidth > 1 ? "0".repeat(defWidth) : "0"))
```

→ `rst_n` 恒 0 → **复位一直有效** → `q` 恒 0。

**已复现**（`tools/e2e-sim.mjs` 用例 2）：
画布信号名 `sys_clk`/`enable`（与端口 `clk`/`en` 走 fuzzy 匹配上了，但 `rst_n` 无信号可配）
→ `rst_n<-null[unbound]` → `rst_n = 1'b0` 全程 → `q = 0000 × 16`。

### 第二条路径：激励全 x → 输出全 x（用户同样会看成"没变化/恒 0"）

`defaultInputValues`（`js/sim.js:50-54`）给「添加端口信号到画布」新建的信号填**全 "x"**。
用户若不画波形就点 Sim，TB 里只有一条 `clk = 1'bx;`，输出恒 x。

即使画全了也不保险：`counter` 的 `q` 无初值，**从未经历复位沿时 x 会自我传播**（`x+1 = x`），
所以「rst_n 恒 1」同样输出全 x。**必须有一个 0→1 的复位释放沿**，计数器才起步。

### fuzzy 匹配的隐患（实证）

`matchSignalsToPorts`（`js/sim.js:487-492`）用 `a.includes(b) || b.includes(a)`：
- 端口 `en` 会匹配上信号 `enable`；端口 `clk` 匹配 `sys_clk`（本次恰好正确，但纯属侥幸）
- 端口 `d` 会匹配 `data`/`addr`/`valid` 中任一 —— **误配风险真实存在**

前任在文档里怀疑过这点，但未实证。本轮证实：`sys_clk`→`clk`、`enable`→`en` 均为 `[fuzzy]`。

## 三、★ 对前任结论的重要修正

**前任把「两侧 stride 口径不一致」列为「恒为 0 的头号嫌疑」——这是错的。**

实证（`tools/_probe-read.mjs` 结论，已并入长期记忆）：

| 场景 | readWaveDocument 结果 |
|---|---|
| 子步数=0，画布 values 长度 = timeSteps | ✅ 正确（走 `length <= timeSteps` 直取分支） |
| 子步数=2（values 长度 = timeSteps×3） | ✅ 正确（stride=3 两侧一致） |
| **子步数=0 但 values 长度 = timeSteps×2** | ❌ 错位半格（stride bug 发作），**但结果非全 0** |

即：stride bug 只在「通过 `addPortSignalsToCanvas` 添加信号（`canvasEffectiveCount()` 按 2 倍长度建信号）」时才发作，
症状是**错位半格**，不是恒 0。**它是真 bug、该修，但不是「恒为 0」的原因。**

另外发现同类问题：`toNativeSignal`（`sim-bridge.js:250`）把注入信号的 `subSteps` **硬编码为 1**，
与画布 `m_subStepCount` 又是一处口径不一致（导致注入信号长度 = timeSteps×2，而原生信号是 timeSteps×1）。

**我上一轮的用例构造不忠实**：

- 上一轮我构造 2 倍长信号时，把用户绘制的值**填满了整个 2 倍长度**
  （`double()` 把每个值重复两次）。
- 真实情况是：`writeValue` 用 `wpf.stride() = 1`，只写 `index = step`，
  **只覆盖前半段 0..23，后半段 24..47 从未被写入**。
- 于是仿真按 stride=2 采样时，cell ≥ 12 全部落进未绘制区，采到 x → 激励几乎全 x。

**前任的判断（stride 是主因）完全正确。** 已在 `MEMORY.md` 中加醒目标注纠错，
并记下教训：构造用例必须忠实模拟真实绘制行为。

## 八、修复内容（commit 5340a8f）

**根因 1 —— stride 口径不一致**（`js/sim-bridge.js`，主因）
- `canvasSubSteps()`：`Math.max(1, Number(dw?.m_subStepCount || 1) || 1)` → `Math.max(0, Number(dw?.m_subStepCount) || 0)`
- `readWaveDocument()` 的 `subSteps` 字段 → 直接复用 `canvasSubSteps()`
- `toNativeSignal()` 的 `base.subSteps = 1` → `canvasSubSteps()`
- 效果：24 步画布建出 len=24 的信号（原来是 48）；回填信号长度与原生一致

**根因 2 —— 未绑定端口默认激励语义**（`js/sim.js`）
- 新增 `resetPolarity()` / `resetInactiveLevel()`
- 未绑定输入端口：低有效复位给 `1`（释放），其余给 `0`（原来一律给 0，导致 rst_n 恒有效）

**根因 3 —— 补 X-4 上电复位脉冲**（`js/sim.js`，前任标为"可选"而漏做）
- 新增 `ensureResetPulse()`：复位端口从未出现有效电平时，前 2 格拉有效、其余释放
- 用户已画复位沿则**完全不改动**（只影响生成的 TB，不改动画布）
- 必要性：DUT 的 reg 无初值保持 x，`x + 1 === x`，没有复位沿计数器永远出不了 x
