## 四、P3 默认浅色主题

探明机制（详见 MEMORY.md「主题机制」一节）：
- 主题 = `body.dark` class；CSS `:root` 默认本就是浅色，深色只是覆盖
- **混淆核心是顶层脚本（非 IIFE）**，`applyTheme` 是全局函数且会持久化
- `WavePaintSkins`（Black/Sunset/Forest，全深色系）只影响波形颜色，与背景无关

实现在 `js/feature-common.js`：启动时调 `window.applyTheme('light')`，
用 `localStorage` 标记 `wpf.defaultLightThemeApplied` **只干预一次**
（改默认值而非锁死主题，用户后续选择一律尊重），
并用 MutationObserver 观察 10s 窗口防止被核心异步改回深色。

## 五、P4 收紧 fuzzy 端口匹配

旧实现 `find(s => a.includes(b) || b.includes(a))` 会让端口 `d` 误配到
`data`/`addr`/`valid`，且同一信号可被多个端口共用。改为：
1. 单字符端口名（d/q 等）**不参与**模糊匹配
2. 长度比 < 0.3 不配对
3. 每个信号只能被一个端口占用（一对一 `claimed` 集合），候选中取最相似者
4. 精确匹配仍优先

`sys_clk→clk`、`enable→en` 这类命名风格差异照旧可匹配（已回归验证）。

## 八、★ 第五轮：用户提 6 个问题的分析（未改代码，仅调研）

用户明确「此段对话暂不进行代码的更改」。以下是**已定位的根因**，供下一轮直接实施。

### 通用前提：混淆核心的字符串被拆分，grep 完整名搜不到

例如 `valueToLabel` 在核心中写作 `[_0x541265(0x60f)+'el']`，
直接 grep `valueToLabel` 结果为 0。**必须用「搜片段 + 提上下文」的方式**（见长期记忆方法论）。

### 问题1 总线进制（DEC 显示错 + 0x/0b 前缀）

核心 `valueToLabel`（wavepaint.63e6dade.js）实现为：
```js
valueToLabel(value, radix) {
  if (-1 === value) return 'X';
  switch (radix) {
    case Radix.Binary:  return '0b' + value.toString(2);
    case Radix.Decimal: return value.toString(10);
    default:            return '0x' + value.toString(16).toUpperCase();
  }
}
```
**它假定 value 是数字，但矢量信号 values 存的是字符串位串**（如 `"0011"`）。
字符串的 `toString(radix)` 忽略参数、原样返回，于是：
- dec → `"0011".toString(10)` = `"0011"` ← **decimal「有问题」的真正原因**
- bin → `"0b0011"`、hex → `"0x0011"` ← **前缀来源**

修法：改用 `js/model.js` 的 `formatVectorValue(value, width, radix)`
（用 `BigInt('0b'+bits)` 转换，dec 正确）；并去掉 hex 的 `0x` 前缀。
`wpf.applyBusRadix`（feature-common.js:320）目前用的是 `dw.valueToLabel`，需换掉。

右键菜单：核心里有一项 `'Value radix: X → Y'`，是**单信号的循环切换**（radix→(radix+1)%3），
核心不可改，需在捕获阶段接管或渲染后替换。**核心菜单的 DOM 结构尚未探测，下一轮先探测。**

### 问题2 整步/子步对总线不生效

`js/feature-draw.js:33` `isPaintableSignal()` 只认 `signal.type === SignalType.Bit`
→ 总线的绘制完全交给核心，我们的 `wpf.writeValue`（含整步/子步粒度）**根本没被调用**。

### 问题3 编辑模式选择总线的效果

`js/feature-select.js:143` `regionSignals()` 只收集 Bit，
**矢量信号被跳过**（文件头注释也承认"批量设值只作用于 Bit 类型信号"）。
结果：框选虽覆盖了总线行，但设1/设0/翻转/复制/粘贴对总线全部无效。

### 问题4 clock 预填应「子步翻转一次」

我第四轮写的 `typicalWaveform` 生成的是**主步序列**（`i % 2`），
经 `toNativeSignal` 铺开时每步的主值被重复 stride 次 → **每 stride 格才翻转一次**（整步翻转）。
用户要的是**每格翻转**（子步级），与示例中的 CLK 一致。

另：`js/feature-templates.js:35` 有同类 stride bug
`Math.max(1, (Number(dw.m_subStepCount) || 1) + 1)` —— 子步 0 时 `0 || 1` = 1 → stride 错算成 2。
（与 sim-bridge.js 修过的那个是同一类问题，需一并修）

### 问题5 画布延长时的填补

`js/feature-resize.js` 已有智能延续（`extendValue`）：
- `sig.isClockPattern` → 按 `detectPeriod` 周期延续 ✓
- 其他 → 延续最后一个确定值

但 `resizeSignals` 重建时（第 108-113 行）**把每个主步的所有子格都填成主值**，
会把子步级方波抹平成整步 —— 与问题 4 同源。
reset 信号延续最后值（=1）行为其实正确，但缺少与 `typicalWaveform` 的统一规则来源。
