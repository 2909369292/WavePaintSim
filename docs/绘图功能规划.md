# WavePaintSim 绘图功能规划文档

> 基于对混淆源码、数据模型、现有功能与主流波形工具（TimeGen / GTKWave / Sigrok PulseView / WaveDrom）的深入研究。
> 日期：2026-08-30

---

## 一、现状分析（研究结论）

### 1.1 代码架构

```
index.html
 ├─ lib/wavedrom-skin.js, lib/wavedrom.min.js     ← WaveDrom 渲染引擎（开源，可读）
 ├─ js/wavepaint.63e6dade.js                       ← 绘图核心（深度混淆，obfuscator.io）
 ├─ js/step-commit-patch.js                        ← 步数提交 patch（非混淆，可扩展）
 ├─ js/zh-lang-patch.js                            ← 中文翻译 patch
 └─ js/sim-bridge.js (ES module)                   ← 仿真面板（我们自己写的）
```

**混淆核心特点**：
- 变量名全部十六进制混淆（`_0x49c406` 等），函数 49 个
- **字符串也被运行时解码**（主字符串表 `_0x49c406` 6632 项，内容为 base64 变体编码，非明文）
- 直接修改混淆代码：**不可维护、极易出错、无法 review**

### 1.2 核心数据模型（关键发现）

```
document_wave
 ├─ m_sampleCount    : 时间步数（UI"步数"，默认 30）
 ├─ m_subStepCount   : 子步数（UI"子步数"，默认 1）
 └─ m_signals[]      : Signal 对象数组

Signal 字段（实测）：name / type(Bit|Vector|BlankRow) / values / labels /
  segmentStyles / driveStrengths / clockMarkers / waveDromColorCodes /
  color / fill / riseTime / fallTime / edgeArrow / radix /
  isClockPattern / clockHighSamples / clockLowSamples / groupName / ...

⚠ 关键：values 长度 ≠ 步数，而是
    values.length = m_sampleCount × (m_subStepCount + 1)

实测：
  步数30 / 子步1 → values 长度 60
  步数30 / 子步2 → values 长度 90
  步数50 / 子步1 → 改步数后长度 100（原版自动 resize）
  步数20 / 子步1 → 长度 40

位值编码（window.__wpConstants.WaveValue）：
  0=低, 1=高, -1=未定义(x), 2=高阻(z), 3=上拉(u), 4=下拉(d)
```

**绘制坐标模型**（mapCanvasPosition 实测）：
- 每个时间步宽 = stepWidth（如 48px），内部分 `(subSteps+1)` 个子格（子步宽 16px）
- `effectiveCount = sampleCount × (subSteps+1)`（如 90）
- 坐标 → `mainStep`(主步) / `subStepFraction`(子步) / `signalSampleIndex`(values 下标)

### 1.3 现有功能清单（工具栏 / 菜单可见）

| 类别 | 功能 |
|---|---|
| 信号添加 | 位信号、矢量信号、空白行；预定义：时钟/计数/复位/脉冲/选通/PWM/斜坡/走查1/走查0/总线空闲/交替/格雷码 |
| 绘制工具 | 画笔、橡皮擦、选择、箭头、时间跨度、标记、时间跳转、文本标注、选择对象、属性 |
| 位状态 | 0/1/z/x/u/d 选择器（Photoshop 风格） |
| 编辑 | 撤销、重做、剪切、复制、粘贴、删除、清除所有信号 |
| 视图 | 缩放、适应窗口、主题、时间轴、轴隐藏、WaveDrom 代码、VCD 信号面板 |
| 导入导出 | WaveDrom JSON、VCD、PNG/SVG/JPG、TXT、CSV |
| 仿真 | Parse / 添加信号(端口识别) / TB / Sim（iverilog 真实仿真） |

### 1.4 发现的问题（与"格式严谨性"相关）

1. **我们添加的端口信号 values 长度 = 步数（×1）**，而原版模型是 `步数 × (子步+1)` —— **不一致**！
   这是用户感觉"波形格式不严谨"的根本原因，也影响仿真采样与导出。
2. **步数变化时**原版自动 resize（保留前部、尾部补空/截断），但补空是"未定义"，且无插值。
3. **点击绘制**依赖先选位状态（0/1/x/z...），无法"上移画1、下移画0"（TimeGen 风格）。
4. 无键盘快捷键绘制。

## 二、重构 vs 直接修改？——决策建议

### 结论：**不建议直接改混淆代码，也不建议一次性全量重构**

| 方案 | 风险 | 成本 | 结论 |
|---|---|---|---|
| A. 直接修改混淆 JS | 字符串运行时解码、变量名混淆，无法安全编辑 | 高（每次改都要解码定位） | ❌ 不可取 |
| B. 一次性用 TS/JS 重写核心 | 143 万字符功能庞大，重写会丢失大量原版细节（缩放/导出/分组/撤销栈…），回归测试成本极高 | 极高 | ❌ 不可取 |
| C. **新增独立 feature 模块 + 原型覆写 + DOM 事件接管** | 低（混淆核心只当"引擎"，不触碰） | 中 | ✅ **推荐** |

### 推荐架构：混合分层（继续沿用现有 patch 模式）

```
┌─────────────────────────────────────────────┐
│ 混淆核心（引擎）: 渲染 / 撤销栈 / 导入导出 /    │
│   预定义信号 / 缩放 / 分组 …                 │
└──────────────▲──────────────────────────────┘
               │ 通过 window 全局 API / DOM 事件 / 原型覆写 交互
┌──────────────┴──────────────────────────────┐
│ 新增非混淆模块（feature-*.js，按需加载）        │
│  ├─ 数据模型修正（values 长度 ×(子步+1)）       │
│  ├─ TimeGen 式鼠标绘制（接管 canvas 事件）      │
│  ├─ 步数自适应增强（插值/延续）                 │
│  ├─ 键盘快捷键                                │
│  └─ 其它增强（波形生成器/测量光标/模板库…）      │
└─────────────────────────────────────────────┘
```

**具体手段**：
1. **数据层**：读取/修正 `document_wave.m_sampleCount / m_subStepCount / m_signals[i].values`
2. **交互层**：在 `wave-canvas` 上**捕获阶段监听** mousedown/mousemove/mouseup（类似 step-commit-patch 的 `stopImmediatePropagation`），完全接管或与原有逻辑共存
3. **渲染层**：必要时调用 `window.drawWaveform()` 重绘；复杂场景才 monkey-patch `drawBitSignal`
4. **保留**：原有撤销栈（通过原版 API 触发）、导入导出（直接调 `exportToWaveDrom` 等）

> 若未来需要彻底摆脱混淆代码：先在"引擎"之上建立**完整行为测试**（记录所有原版输出），再按 数据层 → 渲染层 → 交互层 逐步用可维护代码替换，每步回归。

## 三、功能规划（按优先级分阶段）

### 阶段一（P0）：数据模型严谨性修复 —— 最优先

| # | 功能 | 说明 | 实现 |
|---|---|---|---|
| 1.1 | **添加信号长度对齐原版模型** | 端口信号 `values.length = 步数 × (子步+1)`，全 x | 修改 `sim-bridge.js addPortSignalsToCanvas`：`new SignalCtor(name, type, sampleCount × (subSteps+1))` |
| 1.2 | **画布→仿真采样规则** | 明确每步 (子步+1) 个值中哪个参与仿真（建议：取每步第 1 个值 = 主值） | 修改 `readWaveDocument` 按 `×(subSteps+1)` 步长抽样 |
| 1.3 | **VCD / WaveDrom 导出严谨化** | 导出 wave 字符串按主步生成，含 x/z 语义；导入时按模型补全 | 包装 `exportToWaveDromString` / `importFromWaveDrom` |
| 1.4 | **统一步数语义** | `canvasTimeSteps()` 返回主步数；新增 `canvasEffectiveCount()` 返回 `主步×(子步+1)`；两处调用点统一 | `sim-bridge.js` |
| 1.5 | **子步数变化联动** | 修改子步数时信号自动 resize（复用原版逻辑或接管） | 事件接管 |

### 阶段二（P1）：TimeGen 式鼠标绘制（用户点名需求）

| # | 功能 | 说明 | 实现 |
|---|---|---|---|
| 2.1 | **垂直位置决定 0/1** | 鼠标在信号带内：靠上 = 画 1，靠下 = 画 0（类似 TimeGen） | 接管 canvas `mousedown`：用 `mapCanvasPosition(x,y)` 得 `signalIndex`，用 y 相对信号带高度比例判定 0/1 |
| 2.2 | **按住拖动连续绘制** | 左键按住拖动：连续写 0 或 1（不依赖单次点击） | 接管 `mousemove`，逐格写入 + 节流 |
| 2.3 | **保留高级位值** | 通过位状态选择器或键盘切到 x/z/u/d 时，仍按"固定值"绘制 | 状态机：模式=自动(0/1) / 固定(选择的值) |
| 2.4 | **平滑过渡** | 鼠标进入新信号行时自动切换目标信号 | 用 `mapCanvasPosition().signalIndex` |

### 阶段三（P1）：步数/子步变化自适应（用户点名需求）

| # | 功能 | 说明 | 实现 |
|---|---|---|---|
| 3.1 | **增大步数：智能延续** | 原版尾部补"未定义"→ 增强为：时钟按周期延续、其它信号延续最后值或插值 | 接管 `sample-spin` change，重写 resize 算法 |
| 3.2 | **减小步数：截断 + 提示** | 截断并保留（可撤销） | 复用撤销栈 |
| 3.3 | **子步数变化同步** | 子步从 1→2 时，values 从 ×2 变 ×3，插入中间值 | 同上 |

### 阶段四（P2）：编辑效率增强

| # | 功能 | 说明 |
|---|---|---|
| 4.1 | **键盘快捷键** | 数字 0/1/X/Z 直接切换绘制值；方向键移动光标；Ctrl+Z/Y 撤销重做；Delete 清除 |
| 4.2 | **选择工具批量操作** | 框选区域：批量设 0/1/x、翻转、清除、复制粘贴 |
| 4.3 | **时间光标/测量** | 十字光标、两点时间差、频率显示（类似 GTKWave） |
| 4.4 | **边沿对齐辅助** | 显示上升/下降沿对齐参考线，方便对齐多个信号 |

### 阶段五（P3）：高级绘图功能

| # | 功能 | 说明 |
|---|---|---|
| 5.1 | **波形生成器** | 任意波形：正弦/三角/锯齿/随机；带毛刺的时钟；带建立/保持时间的读写时序模板 |
| 5.2 | **总线增强** | 多进制显示切换（hex/dec/bin）、位字段标注、总线分组/折叠 |
| 5.3 | **模板/片段库** | SPI / I2C / UART / AXI 握手等常用协议波形一键生成 |
| 5.4 | **信号层次树** | 分组/折叠（VCD 层次导入后）
| 5.5 | **缩放增强** | Ctrl+滚轮缩放、子步级放大 |
| 5.6 | **导出增强** | 高清 PNG 缩放因子、SVG 矢量保留、VCD 带 scope 层次、TXT/CSV 带进制选项 |

### 阶段六（P3）：代码卫生

| # | 功能 | 说明 |
|---|---|---|
| 6.1 | 功能模块化 | `feature-draw.js`、`feature-model.js`、`feature-shortcuts.js` 等独立文件，index.html 按需加载 |
| 6.2 | 建立测试页 | 纯前端回归测试（数据结构、resize、绘制坐标） |
| 6.3 | 文档 | 数据模型说明、功能清单、patch 说明 |

## 五、建议实施顺序

1. **P0-1 修复添加信号长度**（半天）→ 消除"格式不严谨"
2. **P1-2 TimeGen 绘制**（1 天）→ 用户点名，体验提升最大
3. **P1-3 步数自适应**（半天）
4. **P2 快捷键 + 测量光标**（1 天）
5. **P3 按需迭代**（波形生成器 → 模板库 → 总线增强）

> 所有阶段均不触碰混淆核心，通过新增 `feature-*.js` + 事件接管 + 原型覆写实现，保持现有架构干净可维护。
